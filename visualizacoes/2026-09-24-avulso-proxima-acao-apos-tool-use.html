Referência técnica breve

O molde para qualquer questão “chegou o stop_reason X, e agora?” material

  1. O que o stop_reason significa? (tool_use = turno suspenso para pedir ferramentas)
  2. Claude terminou? (com tool_use, não: o texto que veio junto não é a resposta)
  3. Quem faz o que falta? (a aplicação extrai name/input/id e executa)
  4. O que volta, e em que forma? (histórico completo + um tool_result por tool_use_id, numa única mensagem user)
  5. O que pode vir depois? (novo stop_reason: end_turn encerra, tool_use repete)

A fronteira decisão/execução doc oficial

  • “The model never executes anything on its own.” O modelo emite um pedido estruturado; quem executa é o seu código (ou os servidores da Anthropic, no caso de server tools).
  • Client tools (as que você define com input_schema, e também bash, text_editor, memory, computer, browser) executam na sua aplicação. A resposta traz tool_use e você devolve tool_result.
  • Server tools (web_search, web_fetch, code_execution, tool_search) executam na infraestrutura da Anthropic e aparecem como server_tool_use. Você nunca monta tool_result para elas.
  • O Tool Runner (beta, nos SDKs) executa suas funções e manda os resultados sozinho, mas roda dentro do seu processo, pelo SDK, e não na API. doc oficial
  • A Messages API é stateless: “you always send the full conversational history”. doc oficial

Erros de interpretação frequentes

  • “O texto ‘Vou consultar…’ é a resposta.” Com tool_use, o turno está suspenso material. Mostrar o texto como aviso de progresso pode ser uma escolha de interface simulação. O erro da alternativa A é parar ali.
  • “Reenviar é um retry, então é seguro.” Retry serve para falha transitória (5xx, 529, rede), e os SDKs já fazem isso sozinhos doc oficial. Um 200 com tool_use não é falha: reenviar a mesma entrada devolve o mesmo pedido material.
  • “Declarei as tools na requisição, então a API as executa.” A API recebe só o schema: “Claude never sees your implementation” doc oficial. Quem executa client tools é a aplicação material.
  • “Basta mandar os tool_result, a API lembra do resto.” Não lembra, porque é stateless. Sem a mensagem assistant com os tool_use, os resultados não respondem a nada doc oficial.
  • “O tool_use_id é um id meu.” É o id do bloco tool_use que o modelo escreveu doc oficial.
  • “Um tool_result por mensagem.” Vão todos juntos na mesma mensagem user. Mensagens separadas “ensinam” o modelo a parar de paralelizar doc oficial.
  • “Depois do tool_result vem sempre a resposta final.” Pode vir tool_use de novo: o loop se repete enquanto o stop_reason for tool_use doc oficial.

O que ficou de fora deste recorte

  • Falha de ferramenta com is_error: true (está no simulador irmão).
  • Texto antes dos tool_result na mensagem user (também dá 400).
  • Server tools misturadas com client tools no mesmo turno, e o pause_turn.
  • max_tokens cortando um tool_use no meio; disable_parallel_tool_use; strict: true.
  • Blocos thinking, que precisam voltar intactos no histórico; streaming.
